## 1. Why this plan exists

The current `layoutId` handoff covers **position and size only**:

- Donor unmounts → coordinator records its bounding rect.
- Consumer mounts under the same id → reads the donor's rect as its
  FLIP "First" → animates from the donor's slot to its own.

What's *not* handed off: the donor's **animated visual state** —
`opacity`, `scale`, `rotate`, `backgroundColor`, anything the donor
had reached through its `animate` target. The consumer mounts fresh,
runs its declared `initial` → `animate`, and that transition plays on
top of the FLIP. Concretely: an `initial: { opacity: 0 }` consumer
under a shared `layoutId` fades in *while* sliding from the donor's
slot, even though the donor was fully opaque the instant before. The
user perceives a "fade restart" stacked on the position morph instead
of a single continuous handoff.

motion-react solves this by snapshotting the donor's animated MV
state at handoff time and using it as the consumer's effective
`initial` for properties the donor touched. This plan ships the same
behaviour on top of our existing donate/consume queue + live-node
registry, with no change to the public `layoutId` API.

The result: a consumer under a shared `layoutId` visually picks up
*where the donor left off* — same opacity, same scale, same colour —
and animates from there to its own `animate` target. No fade restart.
No scale snap. The position FLIP and the state handoff resolve in
one continuous transition.

Design intentionally **additive**: code that doesn't use `layoutId`
is unaffected. Existing `layoutId` usage gains the smoother behavior
by default — the change is detectable only in scenarios that
previously looked janky.

## 2. Locked design decisions

Recorded here at plan-write time. Open questions for the implementing
session live in §10 (not §2).

| # | Decision | Locked answer | Rationale |
|---|---|---|---|
| 1 | **Opt-in or default?** | Default — automatic for any `layoutId` element. | The behavior we ship today is "wrong" (visual restart) in exactly the scenarios `layoutId` exists for; nobody wants the old behavior on purpose. |
| 2 | **Which keys get handed off?** | The union of the donor's CURRENT `animate` target keys (whatever the donor was animating-to / had reached when it unmounted). Plus any MV the donor had written via `useMotion({ animate: { x: motionValue } })`. | Anything outside the donor's `animate` is either layout-controlled (handled separately by FLIP) or default (no point snapshotting `scale: 1`). |
| 3 | **Override priority** | Donated values **override** the consumer's declared `initial` for matching keys. Non-matching keys in `initial` fall through normally. | Donation IS the consumer's effective starting state; ignoring it would defeat the whole feature. |
| 4 | **Variant-shaped initial** | If consumer's `initial` is a variant *label* (`"hidden"`), resolve the label first, THEN apply donation overrides on top of the resolved `Target`. | Variant resolution still owns its semantics; donation is a post-resolution patch. |
| 5 | **In-flight spring preservation?** | No. The consumer starts a fresh transition from the donated VALUES to its own `animate` target. The donor's `Animation` instance is discarded. | Preserving an animation instance across element instances is a much bigger change — motion's `animate()` returns per-call controls, not a value-tracking entity. The donor's *settled-at-this-moment values* are what visually matter. |
| 6 | **SSR behavior** | Server render uses the consumer's declared `initial` (no donation exists on the server). First client paint after hydration ALSO uses the declared `initial` if no donor is present at mount — donation is a client-only runtime phenomenon. Consumers mounting via route-swap on the client get the donation. | Snapshot only exists at runtime. SSR/first-paint correctness depends on the consumer's declared `initial` being a sane default — same constraint as today. |
| 7 | **What if a key is a `MotionValue` in donor's target?** | Snapshot the MV's CURRENT `.get()` value at donation. The consumer treats it as a plain initial value (it does NOT subscribe to the donor's MV after handoff — that ref is gone). | MV-in-target's subscription path is per-instance; preserving subscriptions across mounts would require coordinator-owned MVs. Out of scope. |
| 8 | **Donor still in DOM (`findLive` path)** | Snapshot from the live donor's CURRENT MV values via the coordinator's live registry. Same logic as the `consume()` path; just different source of the values. | The `findLive` path already prefers the live `getBoundingClientRect()`; same precedent applies to state. |
| 9 | **Reduced motion** | When `prefers-reduced-motion: reduce`, the handoff still applies (consumer starts at donated values, not at declared `initial`), but the transition to `animate` uses the same reduced-motion fast-path as everything else. | Reduced motion is about transition duration / motion path, not about what state the element shows. Handoff IS the correct visual state. |
| 10 | **Donor's gesture-active state** | If the donor was in `whileHover` / `whilePress` etc. at unmount, snapshot reflects the CURRENT MV values (which include the gesture's effect). Consumer's own `whileHover` etc. trigger fresh on its own pointer events. | Snapshot is "what was visually showing"; gesture identity does NOT transfer. The mouse may or may not still be over the consumer's slot at mount; the consumer's gesture machine decides from its own events. |

## 3. Public API surface

**No new exports.** No new options. The behavior change is internal to
`createMotion` + `layout-coordinator.ts`. The only externally visible
change is that `layoutId` consumers no longer flash through their own
`initial` after a handoff.

If, during implementation, an opt-out hatch is genuinely needed (e.g.,
a user wants the old fade-restart behavior for stylistic reasons),
add a `MotionOptions.layoutIdInheritState?: boolean` option defaulting
to `true`. Default to **not adding it** unless a test or demo proves
the need — every new option widens the API surface.

## 4. Implementation

### 4.1 Extend the `LayoutEntry` shape

Currently:

```ts
export type LayoutEntry = {
  el: Element
  rect: DOMRect
  projectionParentRect: DOMRect
}
```

Add a snapshot of the donor's user-controlled MV values at donation
time:

```ts
export type LayoutEntry = {
  el: Element
  rect: DOMRect
  projectionParentRect: DOMRect
  /**
   * Snapshot of the donor's user-controlled MV values at donation
   * time, keyed by motion key (CSS prop name or transform component).
   * Captures only the keys the donor's `animate` target touched —
   * not defaults. Consumer applies these as a post-resolution patch
   * on top of its own declared `initial`. Empty object if the donor
   * had no active `animate` keys.
   */
  values: Record<string, number | string>
}
```

### 4.2 Donor capture (donation side)

In `createMotion.ts`, the existing `onCleanup` that calls
`coordinator.donate(...)` (around line 853 — search for "layoutId
donate"): in addition to the `rect` + `projectionParentRect` it
already captures, also build the `values` snapshot by reading the
current value of every MV the donor's `MotionValueRegistry` has
allocated for animation keys.

Pseudocode:

```ts
const values: Record<string, number | string> = {}
const animateKeys = currentAnimateKeysOf(initialOpts)  // see below
for (const key of animateKeys) {
  const mv = registry.peek(key)  // non-allocating read
  if (mv !== undefined) {
    values[key] = mv.get()
  }
}
coordinator.donate(layoutId, { el, rect, projectionParentRect, values })
```

`currentAnimateKeysOf` resolves the donor's CURRENT (last-evaluated)
`animate` target to a flat key list. Variant labels resolve through
the donor's `variants` map. Layered transform internals (`layer.x`,
`layer.scaleX`, etc.) are **excluded** — those are layout's own
channel and are handled by the FLIP itself.

For the `findLive` path: the coordinator's `findLive` returns the
donor's `Element`. To read MV values from a live donor, the
coordinator must also expose the donor's registry (or a value-read
function). Simplest shape: extend the live registry from
`Map<string, Set<Element>>` to
`Map<string, Set<{ el: Element; snapshot: () => Record<string, number | string> }>>`,
where `snapshot` is a closure the donor registered at mount that
reads its current values. The consumer calls `snapshot()` to capture
"what's showing right now."

### 4.3 Consumer apply (consumption side)

In `createMotion.ts`, both the `findLive` and `consume` branches
currently produce only an `initialFirst` rect (lines 798-826). Extend
each to also produce an `initialValues: Record<string, number | string>`
patch derived from the donor's snapshot. Pseudocode:

```ts
let initialFirst: ...
let initialValues: Record<string, number | string> | undefined

if (liveDonor !== null) {
  initialFirst = computeFirstFromRect(liveDonor.el.getBoundingClientRect())
  initialValues = liveDonor.snapshot()
} else {
  const entry = coordinator.consume(layoutIdAtMount)
  if (entry !== null) {
    initialFirst = computeFirstFromRect(entry.el.isConnected
      ? entry.el.getBoundingClientRect()
      : entry.rect)
    initialValues = entry.values
  }
}
```

The `initialValues` patch is then merged into whatever `Target` the
consumer resolves for its declared `initial`:

```ts
const declaredInitial = resolveInitial(opts, variantsCtx)  // existing
const effectiveInitial = initialValues !== undefined
  ? { ...declaredInitial, ...initialValues }
  : declaredInitial
applyInitialStyle(el, effectiveInitial)
```

Donor values override declared initial **per locked decision #3**.

### 4.4 SSR

`computeInitialStyle` (server) cannot see donations — donations are a
client-runtime concept. The server emits the consumer's declared
`initial` as today; this is correct because:

- No donor exists in the server-rendered tree at this point.
- The hydration handshake (`data-motion-hydrated=""` + SSR-applied
  style) means the first client paint matches the server.
- Donation only happens at consumer MOUNT, which is post-hydration.
- A route-swap mount in the browser is the trigger for donation, and
  by definition that's not part of SSR.

Net: no SSR changes required.

## 6. Tests — what to write

Place in `packages/motion/tests/layout/state-handoff.test.tsx`.

| Test | What it verifies |
|---|---|
| `opacity is inherited from donor` | Donor unmounts with `opacity: 0.5`; consumer mounts with `initial: { opacity: 0 }`. The consumer's first style write is `opacity: 0.5`, not `0`. After `animate` resolves, opacity ends at consumer's declared `animate.opacity` (or `1` if absent). |
| `scale handoff while position FLIPs` | Donor at `scale: 1.5`. Consumer mounts at a different slot with `initial: { scale: 1 }`. Effective initial: scale 1.5 at donor's position. Single transition resolves both to consumer's target slot at consumer's target scale. |
| `consumer-only keys fall through` | Donor touched only `opacity`. Consumer declares `initial: { rotate: 45 }`. Effective initial: donor's opacity + consumer's rotate 45. Rotate is NOT zeroed by the donation. |
| `variant label initial` | Consumer declares `initial: "hidden"` where `variants.hidden = { opacity: 0, x: 100 }`. Donor had `opacity: 1`. Effective initial: `{ opacity: 1, x: 100 }` — variant resolved, then donation patched on. |
| `live donor path` | Two siblings mounted under same `layoutId` (Presence keep-alive case). Donor still in DOM with `opacity: 0.3`. Consumer mount: snapshot reads donor's CURRENT MV value via the live registry; effective initial reflects 0.3. |
| `MotionValue in donor target` | Donor's animate had `{ x: someMv }` where `someMv.get() === 80` at donation. Consumer's effective initial.x is `80` (plain value, not subscribed to the MV). |
| `reduced motion path` | With `matchMedia('(prefers-reduced-motion: reduce)')` mocked true, handoff still applies: effective initial picks up donor's values; consumer's transition resolves instantly. |
| `no donor → declared initial` | Consumer mounts under a `layoutId` with NO prior donor and NO live sibling. Effective initial === declared initial. No regression vs. today. |
| `SSR pass-through` | Server-rendered `<motion.div layoutId="x" initial={{ opacity: 0 }} />` emits `style="opacity:0"`. No `values` artifact in the output. |
| `donation expires by RAF` | Donor unmounts. Consumer mounts >2 RAFs later. Effective initial === declared initial (donation expired with the rest of the queue entry). |

Plus a typecheck/expectTypeOf assertion in `tests/types.test-d.ts`
that `LayoutEntry.values` exists and is `Record<string, number | string>`.

## 10. Open questions deferred to the implementing session

These were noted during plan-write but not locked:

1. **Snapshot thunk allocation cost.** Registering a `snapshot`
   closure per `layoutId` element on every mount adds a small heap
   allocation. Negligible at typical use but worth confirming under
   stress (1000+ items). If it shows up in profiling, hoist to a
   shared per-coordinator function that takes the registry as an
   argument.
2. **Multiple live siblings.** Today's `findLive` returns "any other
   live element." If multiple donors are alive at consume time
   (Presence with overlapping exits), which one's state wins?
   Recommendation: stick with current "first non-self" semantics and
   document the indeterminacy. The position FLIP has the same
   indeterminacy today.
3. **`transition` for the handoff.** The consumer's own `transition`
   prop drives the morph. There's no per-key transition override
   ("use the donor's spring for opacity only"). Recommendation:
   don't add one. Single transition for the whole morph reads as one
   continuous motion, which is the goal.
4. **Interaction with `whileDrag` gate (ADR 0008).** A consumer that
   mounts mid-drag of a donor is exotic — none of the existing demos
   hit it. Recommendation: punt to a separate test scenario if a
   user reports the case.

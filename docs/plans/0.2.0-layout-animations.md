## 1. Why this plan exists

The 0.2.0 release ships an API consistency audit
([docs/plans/0.2.0-api-audit.md](0.2.0-api-audit.md)) AND layout
animations. The audit is mostly done; this plan covers layout
animations as a separate, self-contained body of work.

The full motion-react feature surface is in scope:

1. **`layout`** — auto-animate a motion element when a Solid render
   changes its measured bounding rect. FLIP (First-Last-Invert-Play)
   is the implementation primitive.
2. **`layoutId`** — match motion elements across mount/unmount so a
   transition animates between them (shared-element transitions).
3. **`<LayoutGroup>`** — coordinator/namespace for `layoutId`,
   measurement broadcaster, and sibling-synchronization point.
4. **`layoutScroll`** — declare an ancestor as a scrollable container
   so descendants' layout animations correctly compensate for its
   scroll position.
5. **`layoutRoot`** — override projection ancestry. Declares an element
   as the reference frame for descendants' layout animations (used
   for fixed-positioned panels that break normal flow).
6. **`layoutAnchor`** — `{ x: 0..1, y: 0..1 }` parent-relative pivot
   point for layout animations.

## 2. Locked design decisions

All choices were grilled in a design session and recorded in
[CONTEXT.md](../../CONTEXT.md) and two ADRs. Summary:

| # | Decision | Locked answer | Reference |
|---|---|---|---|
| 1 | **Scope** | All 6 features ship in 0.2.0 | §1 above |
| 2 | **Measurement triggers** | Style-write interception + `ResizeObserver(self)` + `MutationObserver(parent, { childList })` + `LayoutGroup.dependency` + per-element `layoutDependency`. All trigger sources feed into `frame.read`-batched measurement. | This plan §4 |
| 3 | **Transform composition** | Option A — reserved keys (`_layoutX`, `_layoutY`, `_layoutScaleX`, `_layoutScaleY`) in the existing value registry; fixed composition order in the writer | ADR 0006 |
| 4 | **layoutId coordinator** | Implicit root LayoutGroup + explicit `<LayoutGroup>` for scoping. Donate/consume API with RAF-bounded entry lifetime. Presence-aware (donor stays alive during exit) | This plan §6 |
| 5 | **Entry lifetime** | Entries written at `onCleanup` survive until consumed OR the next `requestAnimationFrame` (idempotent RAF cleanup per coordinator) | This plan §6 |
| 6 | **layoutId × exit** | Parallel-running. Exit animates on the donor; FLIP animates on the consumer. No cross-cancellation. | This plan §6 |
| 7 | **Nested measurement** | Approach 2 — projection-parent-local coordinates via Solid context. No projection-node-tree. | ADR 0007 |
| 8 | **Top-level projection parent** | `document.documentElement` (scroll-stable, no separate scroll-compensation pass at the root) | ADR 0007 |
| 9 | **`layout` modes** | `boolean \| "position" \| "size" \| "preserve-aspect"` (motion-react parity) | This plan §3 |
| 10 | **Dependency typing** | `Accessor<unknown>` only (no static-value form); intentionally stricter than the audit's `Accessor<T> \| T` convention for clarity | This plan §3 |
| 11 | **Transition resolution** | `layoutTransition` (most specific) → `transition` → `<MotionConfig>.transition` (least specific) | This plan §3 |
| 12 | **LayoutGroup shape** | Fragment-only component (no DOM wrapper). Single prop in 0.2.0: `dependency`. `id`-based cross-group namespacing deferred. | This plan §3 |

## 3. Public API surface

### 3.1 `MotionOptions` additions

Append to [`packages/motion/src/types.ts`](../../packages/motion/src/types.ts)'s
`MotionOptions` definition:

```ts
import type { Accessor } from "solid-js"

export type MotionOptions = MotionCallbacks &
  DragOptions & {
    // ... existing animate / initial / hover / press / etc. ...

    /**
     * Auto-animate when a Solid render changes the element's measured
     * bounding rect (FLIP). Boolean shorthand for `true` animates both
     * position and size. Strings narrow the animation:
     *
     * - `"position"` — translate only; size changes are instant.
     * - `"size"` — scale only; position changes are instant.
     * - `"preserve-aspect"` — translate + uniform scale; maintains the
     *   rect's aspect ratio across the FLIP (no anisotropic stretch).
     */
    layout?: boolean | "position" | "size" | "preserve-aspect"

    /**
     * Shared-element identity. Two motion elements with the same
     * `layoutId` (in the same `<LayoutGroup>` scope) match across
     * mount/unmount; the entering element FLIPs from the donor's last
     * position. Independent of `<Presence>` — runs in parallel with
     * the donor's `exit` animation when both are active.
     */
    layoutId?: string

    /**
     * Reactive trigger for layout re-measurement. Use when the cause of
     * the layout change isn't visible to the library's automatic
     * triggers (style-write interception, `ResizeObserver` on self,
     * `MutationObserver` on parent). Accessor form only — explicit
     * function:
     *
     * @example
     * <motion.div layout layoutDependency={() => items().length} />
     */
    layoutDependency?: Accessor<unknown>

    /**
     * Declare THIS element as a scrollable container for the purposes
     * of descendants' layout animations. Descendants whose projection
     * parent is inside this element compensate their measured rects
     * for this element's `scrollLeft`/`scrollTop`, so a user scrolling
     * the container doesn't pollute layout deltas.
     */
    layoutScroll?: boolean

    /**
     * Declare THIS element as the projection root for descendants'
     * layout animations, overriding the nearest `layout` ancestor.
     * Use for fixed-positioned or absolute elements whose visual
     * position differs from their layout-flow position.
     */
    layoutRoot?: boolean

    /**
     * Parent-relative origin point for the layout animation. Each
     * component in 0..1. Default `{ x: 0, y: 0 }` (top-left, standard
     * FLIP behaviour). `{ x: 0.5, y: 0.5 }` pivots the layout
     * animation from the projection parent's center; `{ x: 1, y: 1 }`
     * from the bottom-right.
     */
    layoutAnchor?: { x: number; y: number }

    /**
     * Transition override specifically for layout animations.
     * Resolution chain: `layoutTransition` (most specific) →
     * `transition` (on this element) → `<MotionConfig>.transition`
     * (least specific). Applies to both `layout`-driven FLIPs and
     * `layoutId`-driven shared transitions.
     */
    layoutTransition?: Transition
  }
```

## 4. Measurement triggers — the trigger model

Every `layout` element subscribes to multiple sources. Any source firing
schedules a measurement on the next `frame.read` pass; the scheduler
coalesces all triggered elements into a single read batch.

### Trigger sources (per `layout` element)

1. **Style-write interception** — the value registry's writer routes
   style writes through a known code path. When a layout-affecting key
   is written (width, height, padding, margin, font-size, display,
   position, top/left/right/bottom, flex-*, grid-*), notify the layout
   controller for this element. NOT triggered by transform/opacity/filter
   writes (those don't change `getBoundingClientRect`).

2. **`ResizeObserver(self)`** — fires when this element's box changes
   (size or content-box dimensions). Catches: children pushing our size,
   ancestor restyles affecting our flex/grid sizing.

3. **`MutationObserver(parent, { childList: true })`** — fires when the
   element's direct parent's child list mutates (sibling appears,
   disappears, reorders). Catches the most common case of layout change
   in lists.

4. **`LayoutGroup.dependency` broadcast** — when a containing
   `<LayoutGroup>`'s `dependency` accessor changes, the group's
   broadcast signal bumps. Every descendant `layout` element subscribes
   via context and re-measures.

5. **Per-element `layoutDependency`** — same shape as LayoutGroup's
   broadcast, scoped to this element only.

### Documented gap

A **grandparent-or-deeper ancestor restyle that changes our position
without changing our size, without any wrapping `<LayoutGroup>`, without
`layoutDependency`** is not detected automatically. Document the
escapes:

- Wrap the relevant ancestor in `<LayoutGroup dependency={() => signal()}>`.
- Pass `layoutDependency={() => signal()}` to the motion element.
- For non-Solid sources, compose `createAttributeSignal(ref, ['class'])`
  with either dependency.

### Scheduling: `frame.read` / `frame.write` pipeline

motion-dom's `frame` scheduler is already an internal dependency
(see `createTime` in motion-value.ts). All measurement reads run in
`frame.read(...)` callbacks; layout writes (setting the inverting MVs)
run in `frame.write(...)`. The pipeline batches all reads before any
writes, eliminating layout thrash.

Layout controller pseudo-code:

```ts
function scheduleMeasurement() {
  if (measurementPending) return
  measurementPending = true
  frame.read(() => {
    measurementPending = false
    // Read self.rect AND projectionParent.rect.
    // Compute local-coord Last.
    // If we had a stored First, compute delta; schedule FLIP write.
    // Update First = Last for the next round.
  })
}

function applyFlip(delta) {
  frame.write(() => {
    // Set _layoutX / _layoutY MVs to -delta (the invert).
    // Set _layoutScaleX / _layoutScaleY MVs to inverse scale (if "size"-mode).
    // Animate them to 0 / 1 with the resolved transition.
  })
}
```

## 5. Transform composition (per ADR 0006)

### 5.1 Reserved keys in the value registry

Extend the registry's writer to recognize four reserved keys:
`_layoutX`, `_layoutY`, `_layoutScaleX`, `_layoutScaleY`. They
participate in the transform-string compile alongside user-facing
keys. Reject user writes to these keys at the registry's write API
(`set` should throw or no-op with a dev warning when given a reserved
key from outside the layout module).

### 5.2 Compile order

The compiled `transform` string follows a fixed order:

```
translate3d(_layoutX, _layoutY, 0)            ← layout, outermost
translate3d(x, y, z)                          ← user
rotate(rotate)                                ← user
rotateX(rotateX) rotateY(rotateY) rotateZ(rotateZ)
skewX(skewX) skewY(skewY)
scale3d(scaleX * _layoutScaleX, scaleY * _layoutScaleY, scaleZ)   ← user × layout
```

Composition is mathematical:

- **Translate:** additive. `final_x = x + _layoutX`.
- **Scale:** multiplicative. `final_scaleX = scaleX * _layoutScaleX`.
- **Rotate/skew:** untouched by layout (no reserved keys; pure user).

The writer's compile function gets two new conditional branches: emit
the leading layout translate if `_layoutX` or `_layoutY` is registered;
multiply scales if `_layoutScaleX` or `_layoutScaleY` is registered.
~10 lines of additions.

### 5.3 `layout` mode → which keys are written

| `layout` mode | `_layoutX/Y` written? | `_layoutScaleX/Y` written? |
|---|---|---|
| `true` | Yes | Yes |
| `"position"` | Yes | No |
| `"size"` | No | Yes |
| `"preserve-aspect"` | Yes | Yes (uniform: `_layoutScaleX === _layoutScaleY`) |

For `"preserve-aspect"`, the scale is computed from the larger axis
delta (or the geometric mean — match motion-react during implementation
and verify with a bench).

## 6. `layoutId` coordinator

### 6.1 Coordinator structure

Each `<LayoutGroup>` allocates a coordinator:

```ts
type LayoutEntry = {
  rect: DOMRect                  // donor's last absolute rect (in document coords)
  projectionParentRect: DOMRect  // donor's projection parent's rect at donation time
  // Possibly: in-flight animation state for cross-fade scenarios.
}

class LayoutCoordinator {
  private entries = new Map<string, LayoutEntry>()
  private staleEntries = new Set<string>()
  private cleanupScheduled = false

  donate(layoutId: string, entry: LayoutEntry): void {
    this.entries.set(layoutId, entry)
    this.scheduleCleanup()
  }

  consume(layoutId: string): LayoutEntry | null {
    const entry = this.entries.get(layoutId) ?? null
    if (entry) {
      this.entries.delete(layoutId)
      this.staleEntries.delete(layoutId)
    }
    return entry
  }

  private scheduleCleanup() {
    if (this.cleanupScheduled) return
    this.cleanupScheduled = true
    // Mark all current entries as stale at this point.
    for (const key of this.entries.keys()) this.staleEntries.add(key)
    requestAnimationFrame(() => {
      this.cleanupScheduled = false
      // Drop any entry that survived a full RAF cycle without being consumed.
      for (const key of this.staleEntries) this.entries.delete(key)
      this.staleEntries.clear()
    })
  }
}
```

### 6.2 Implicit root coordinator

A module-level `RootLayoutCoordinator` singleton handles all `layoutId`
elements not wrapped in an explicit `<LayoutGroup>`. Mounts/unmounts
use it by default; wrapping in `<LayoutGroup>` overrides the default
via context.

### 6.3 Donate at `onCleanup`

In `createMotion`, when the element has `layoutId`, register an
`onCleanup` handler:

```ts
onCleanup(() => {
  const layoutId = untrack(getOpts).layoutId
  if (!layoutId) return
  const rect = el.getBoundingClientRect()
  const parentRect = projectionParentRef.getBoundingClientRect()
  coordinator.donate(layoutId, { rect, projectionParentRect: parentRect })
})
```

The `untrack(getOpts)` pattern mirrors Presence's `runExit` (see
ADR 0003) — read the LATEST opts at the moment of donation.

### 6.4 Consume at mount setup

During `createMotion`'s setup, before the first FLIP measurement:

```ts
const layoutId = untrack(getOpts).layoutId
if (layoutId) {
  const donor = coordinator.consume(layoutId)
  if (donor) {
    // Override the First measurement with the donor's rect, converted
    // to this element's projection-parent-local coords.
    // The "First" rect for this element is the donor's last position.
  }
}
```

After consuming, the element's first FLIP measures its natural Last
position; the delta from donor's First to our Last drives the animation.

### 6.5 Presence interaction

When the donor is exiting under `<Presence>`:

1. Donor's `runExit` runs. The exit target animates (e.g., opacity → 0).
2. **Independently**, donor's `onCleanup` runs at the moment Presence
   unregisters and Solid disposes — donate happens then.
3. Consumer mounts. Reads coordinator. Gets donor's last rect.
4. **Both animations now run in parallel.** Donor's exit completes
   on the donor element (which Presence keeps alive in DOM until
   exit settles). Consumer's FLIP runs on the consumer element from
   donor's rect to consumer's natural rect.

No cross-cancellation. No exit suppression. Match motion-react.

### 6.6 Special case — synchronous handoff with donor still alive

When donor and consumer are alive simultaneously (Presence case before
exit settles, or concurrent renders), the consumer can read donor's
**live** rect directly via DOM lookup AND the coordinator's stored rect.
Prefer the live rect when both are available — it reflects any
mid-flight transforms the donor has accumulated. Use the stored rect
only when the donor is gone.

## 7. Projection coordinates (per ADR 0007)

### 7.1 `ProjectionContext`

New Solid context in [`packages/motion/src/projection-context.ts`](../../packages/motion/src/projection-context.ts):

```ts
import { type Accessor, createContext } from "solid-js"

export type ProjectionContextValue = {
  /** The DOM element to measure against (projection parent). */
  parentEl: Accessor<Element>
  /** Scroll-compensation chain: each entry is a `layoutScroll` ancestor's element. */
  scrollAncestors: Accessor<Element[]>
}

const defaultProjectionContext: ProjectionContextValue = {
  parentEl: () => document.documentElement,
  scrollAncestors: () => [],
}

export const ProjectionContext = createContext<ProjectionContextValue>(
  defaultProjectionContext,
)
```

### 7.2 Who pushes context

Both `<motion.X layout>` and `<motion.X layoutRoot>` push themselves as
the new projection parent for descendants. Inside `useMotion` /
`createMotion`'s setup:

```ts
if (opts.layout || opts.layoutRoot) {
  const childContext: ProjectionContextValue = {
    parentEl: () => el,
    scrollAncestors: opts.layoutScroll
      ? () => [el, ...parentContext.scrollAncestors()]
      : parentContext.scrollAncestors,
  }
  // Inject via the JSX-wrapper chain that already pushes motion.Provider.
  // Co-locate with the variant Provider so it stays simple.
}
```

The `<motion.X>` proxy (ADR 0004) is the natural place to attach this —
its unconditional `m.Provider` wrap can also push `ProjectionContext`.

### 7.3 Measurement math

For an element with rect `E` and projection parent rect `P`, in
`layoutScroll`-aware form:

```ts
function measureLocal(el: Element, parentEl: Element, scrollAncestors: Element[]) {
  const E = el.getBoundingClientRect()
  const P = parentEl.getBoundingClientRect()
  let localX = E.left - P.left
  let localY = E.top - P.top
  // Add back each scroll ancestor's scroll offset.
  for (const scroller of scrollAncestors) {
    localX += scroller.scrollLeft
    localY += scroller.scrollTop
  }
  return { x: localX, y: localY, width: E.width, height: E.height }
}
```

For `layoutAnchor`, adjust origin AFTER computing local coords:

```ts
const anchor = opts.layoutAnchor ?? { x: 0, y: 0 }
const PR = parentEl.getBoundingClientRect()
localX -= PR.width * anchor.x
localY -= PR.height * anchor.y
```

## 8. Layout controller (per-element machinery)

New file: [`packages/motion/src/primitives/createLayoutController.ts`](../../packages/motion/src/primitives/createLayoutController.ts).

Responsibilities:

1. Subscribe to all trigger sources (ResizeObserver, parent
   MutationObserver, LayoutGroup broadcast, layoutDependency).
2. Maintain First/Last cache in projection-local coords.
3. Run measurements via `frame.read`; apply inverts via `frame.write`.
4. Drive the reserved-key MVs (animate from inverting delta to identity).
5. Handle layoutId donate/consume.
6. Wire lifecycle callbacks (`onLayoutAnimationStart`, `onLayoutAnimationComplete`).

API sketch (called from `createMotion` when `opts.layout` or
`opts.layoutId` is truthy):

```ts
export function createLayoutController(
  el: MotionElement,
  getOpts: () => MotionOptions,
  projectionContext: ProjectionContextValue,
  layoutGroupContext: LayoutGroupContextValue,
): void {
  // Reads layout-relevant opts on each pass via untrack(getOpts).
  // Owns the four reserved MVs (registered in this element's value registry).
  // Subscribes to triggers; calls scheduleMeasurement on each.
  // Auto-disposed via the surrounding createMotion's onCleanup.
}
```

### 8.1 Animation handoff

When the controller schedules a FLIP write, it uses motion-dom's
`animate()` against the reserved MVs (NOT the user-facing keys). The
transition is resolved via the layoutTransition precedence chain (§3.1).

Lifecycle callbacks fire from the animate's `onStart` / `onComplete`
hooks.

### 8.2 Interruption semantics

If a new measurement triggers while a FLIP animation is in flight:

1. Cancel the in-flight animation on the reserved MVs (its current
   values become the new starting point — naturally captured because
   the MVs already hold them).
2. Re-measure new First (current MV values converted to a delta) and
   new Last.
3. Animate from the current visual state to the new Last.

This is equivalent to the createSpring tempSource pattern (Step 7 of
the API audit) — the visual position is preserved across the
interruption.

  ```ts
    return rafCallbacks.length
  }
  function flushRAF() {
    const cbs = rafCallbacks
    rafCallbacks = []
    for (const cb of cbs) cb(performance.now())
  }
  ```

  Use `flushRAF()` to advance the coordinator cleanup deterministically.

- **`ResizeObserver` / `MutationObserver` stubbing.** Inspired by the
  existing `IntersectionObserver` spy in `scroll-inview.test.tsx`. Each
  test that exercises the trigger model captures observer instances
  and triggers them manually via the captured callback references.

- **`frame.read` / `frame.write` flushing.** motion-dom's frame
  scheduler can be advanced by manually invoking `frame.read.process()`
  / `frame.write.process()` in tests, or by stubbing the scheduler
  entirely. Pattern to be established during implementation.

### 10.3 TDD discipline (mirroring the audit's createSpring/createTransform pattern)

For load-bearing behaviour, write the test against the regression FIRST,
let it fail against a naïve implementation, then ship the fix:

- **Nested over-correction (the canonical Approach 2 motivation):**
  Write a test where parent and child both `layout`-animate; assert
  child's visible position matches its true Last AFTER parent's invert
  is applied. A world-coord (non-Approach-2) implementation will
  over-correct and fail this test.

- **layoutId entry expiration:** test that an entry written at T,
  consumed at T+0.5 RAF tick succeeds; consumed at T+2 RAF ticks
  fails (entry was cleared).

- **Trigger isolation:** test that ONLY style-affecting style keys
  trigger measurement, not transform/opacity/filter writes.

```markdown
### Added — Layout animations

- **`<motion.X layout>`** — auto-animate when a Solid render changes the
  element's measured bounding rect. FLIP under the hood. Four modes:
  `true` (position + size), `"position"`, `"size"`, `"preserve-aspect"`.

- **`<motion.X layoutId="…">`** — shared-element transitions. Two motion
  elements with the same `layoutId` (within the same `<LayoutGroup>`
  scope) match across mount/unmount; the entering element FLIPs from
  the donor's last rect. Runs in parallel with the donor's `exit`
  animation when both are active under `<Presence>`.

- **`<LayoutGroup>`** — fragment-only component scoping `layoutId`
  matches and broadcasting a re-measurement signal to descendants via
  a `dependency` accessor prop. Use when an ancestor restyle drives
  layout shift in descendants (Solid doesn't propagate the way React
  does — see [ADR 0007](../../docs/adr/0007-layout-projection-coordinates.md)).

- **`layoutScroll`** — declares an ancestor as a scrollable container
  for descendants' layout-animation purposes. Their measured rects
  compensate for the container's `scrollLeft`/`scrollTop` so a user
  scrolling doesn't pollute layout deltas.

- **`layoutRoot`** — overrides projection ancestry. Declares an element
  as the reference frame for descendants' layout animations. Use for
  fixed-positioned panels whose visual position differs from their
  layout-flow position.

- **`layoutAnchor: { x, y }`** — parent-relative pivot point for layout
  animations. Default `{ x: 0, y: 0 }` (top-left); `{ x: 0.5, y: 0.5 }`
  pivots from the projection parent's center.

- **`layoutDependency: Accessor<unknown>`** — explicit re-measurement
  trigger for the corner cases where automatic detection doesn't fire
  (deep-ancestor restyles, third-party DOM manipulation).

- **`layoutTransition: Transition`** — transition override specifically
  for layout animations. Resolution precedence: `layoutTransition` →
  `transition` → `<MotionConfig>.transition`.

- **`onLayoutAnimationStart` / `onLayoutAnimationComplete`** — lifecycle
  callbacks for layout-driven animations.

- **`createAttributeSignal(ref, attrs?)`** — Solid-bridge helper that
  produces an `Accessor<number>` incrementing on watched attribute
  mutations. Compose with `layoutDependency` or `LayoutGroup.dependency`
  to bridge non-Solid sources (third-party DOM libs, native HTML
  attributes) into the layout-trigger model.
```

## 14. Migration guide

Layout animations are **purely additive**. No existing code breaks. The
opt-in is `layout` on a motion element. From 0.1.x:

> If you weren't using layout animations: no migration. Existing
> animations, gestures, and drag continue to work unchanged.
>
> If you want to add layout animations:
> 1. Add `layout` to any motion element whose bounding rect changes
>    via Solid reactivity.
> 2. For `<For>` lists, no extra wiring needed — parent-childList
>    `MutationObserver` catches the reorder.
> 3. For shared-element transitions, use `layoutId="…"` on both ends;
>    wrap matched pairs in `<LayoutGroup>` if you want to scope them
>    (otherwise they share the implicit root namespace).
> 4. For cases where layout shifts come from ancestor restyles that
>    aren't visible to the library's automatic triggers, wrap that
>    ancestor in `<LayoutGroup dependency={() => signal()}>` OR
>    pass `layoutDependency={() => signal()}` to the motion element.

## 15. Risk list (read before merging)

1. **Reserved-key naming collisions.** If a future motion-dom or
   upstream-motion update introduces a key starting with `_layout`,
   we'd clash. Mitigation: the underscore prefix is unusual in
   upstream motion APIs (they use camelCase). Document the convention
   as ours.

2. **`document.documentElement.getBoundingClientRect` cost.** Called
   once per `frame.read` pass per top-level layout element. Cheap on
   modern browsers; batched within the same read pass anyway. Not a
   real concern.

3. **`MutationObserver` per parent of every `layout` element.** For
   large lists (1000+ items), this is 1000 MOs on the same parent.
   Mitigation: share a single MO per parent across all `layout`
   children — cache by parent element in a `WeakMap`.

4. **Stale `_layout*` MVs across feature toggles.** If a user turns
   `layout` off (e.g., `layout={isExpanded() ? true : false}`), the
   reserved MVs need to be cleaned up. The layout controller should
   unregister them from the registry and the writer's compile output
   should fall back to user-only transforms.

5. **Interaction with `dragMomentum`.** A drag-release momentum
   animation (motion-dom inertia) can overlap with a layout animation
   if the layout changes during the inertial flight. Test that the
   combined output is sane (drag and layout write different keys; they
   compose additively; no conflicts expected, but verify empirically).

6. **SSR.** Layout animations are entirely browser-DOM-driven
   (`getBoundingClientRect`, `ResizeObserver`, `MutationObserver`,
   `requestAnimationFrame`). On the server, the layout controller
   should no-op cleanly (the createMotion path is wrapped in
   `createEffect`, which already no-ops on the server). Reserved MVs
   shouldn't be created server-side. Verify in `tests/ssr/`.

7. **Reduced-motion mode.** Per `<MotionConfig reducedMotion="always">`,
   layout animations should skip their animation phase — apply the
   inverting transform but instantly tween to identity (no transition).
   Or alternatively, don't FLIP at all and let the change happen
   instantly. Match motion-react's behaviour during implementation.

8. **layoutId entry leak under rapid mount/unmount cycles.** If many
   donors register but no consumers ever appear, the RAF cleanup runs
   each frame and drains the map. Bounded growth at one frame's worth
   of donations. Not a real leak, but worth a test.

9. **Projection-context churn under `<motion.div layout layoutRoot>`
   (both flags).** The element becomes a projection parent for
   descendants AND animates its own layout. Verify the context
   provides a stable ref (the element itself) regardless of whether
   `layout` is currently animating. Implementation note: provide
   `parentEl: () => el` where `el` is captured at mount; never bind
   the accessor to anything that might churn.

## 18. Open implementation questions deferred to the IMPLEMENTING session

These are details that didn't need to be resolved in the design grill;
the implementer should make a reasonable call and document the choice
in code comments:

- **Exact composition string format.** The order described in §5.2 is
  the design commitment; the implementer should verify against
  motion-react with side-by-side comparisons during the
  `tests/layout/composition.test.tsx` build.

- **`"preserve-aspect"` mode's scale-axis choice.** Whether the
  preserved scale uses `Math.max(scaleX, scaleY)`, `Math.min`, or the
  geometric mean. Match motion-react.

- **`frame.read` / `frame.write` ordering for nested elements.**
  Parent should measure BEFORE child (top-down) OR child before parent
  (bottom-up)? Approach 2 makes this less critical (local coords are
  self-contained) but the order may matter for performance. Default
  to no explicit ordering; test for correctness; introduce ordering
  only if a real test fails.

- **`reduced-motion` integration specifics.** When `<MotionConfig
  reducedMotion="always">`, do layout animations skip entirely, or
  do they snap to the new state without a transition (instant FLIP →
  identity)? Probably the latter for visual continuity. Verify with
  the existing `tests/reduced-motion/` patterns.

- **Implicit-root coordinator disposal at HMR / dev-mode hot reload.**
  The module-level singleton survives across reactive owner disposal.
  Confirm that orphaned `layoutId` entries from a previous HMR cycle
  don't pollute the next; if they do, document a reset mechanism.

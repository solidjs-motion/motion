# 0.2.0 — Primitive API consistency audit (+ layout animations)

> **Audience.** A future Claude session (or human contributor) working in a
> separate worktree, branched off `main` after `01d2993` (the 0.1.7 release).
> This document is self-contained: read it top-to-bottom and you have
> everything needed to execute the work without going back to chat history.

> **Branch.** Suggested name `next` (Babel/npm/Express convention — short,
> idiomatic, survives across major bumps). Alternative: `v0.2` if a
> self-documenting branch name is preferred. The choice is the maintainer's;
> the plan body doesn't depend on it.

---

## 1. Why this plan exists

`0.1.7` shipped a `createScroll` bug fix (commit `01d2993`) but **deliberately
did not** ship the API shape change that was originally bundled with it. The
maintainer wanted users on `0.1.x` to get the fix immediately without an API
migration. The API consistency work was deferred to `0.2.0`, where it lands
alongside layout animations (a substantial separate feature).

What `0.1.7` actually shipped that's still relevant to `0.2.0`:

- `createScroll` got a new `trackContentSize?: boolean` option (default `true`)
  and an internal suppression gate that holds the four MotionValues at `0`
  until motion-dom reports a real measurement.
- `makeAccessor` in [`packages/motion/src/primitives/motion-value.ts`](../../packages/motion/src/primitives/motion-value.ts)
  was rewritten to use Solid's `from()` primitive. No API impact — keep this
  as-is for 0.2.0.
- [`packages/motion/src/primitives/createInView.ts`](../../packages/motion/src/primitives/createInView.ts)
  gained a doc-header explaining why we use `IntersectionObserver` directly
  instead of wrapping motion's `inView()`. Keep this as-is.

What was reverted from 0.1.7 to wait for 0.2.0:

- `createScroll`'s public signature still uses **per-field accessors**:
  `container?: () => Element | null` and `target?: () => Element | null`. The
  options-as-accessor migration (`Accessor<CreateScrollOptions> | CreateScrollOptions`)
  is part of this plan.

## 2. Locked design decisions

All five questions were grilled and answered. Summary table:

| # | Decision | Locked answer |
|---|---|---|
| 1 | **Scope** of the audit | Options + refs (don't touch `createMotionValue`'s `initial` arg etc.) |
| 2 | **Type alias** for the function form | `Accessor<T> \| T` everywhere — replace every `T \| (() => T)` |
| 3 | **`createSpring` / `createTransform` options** | Reactive — recreate underlying engine on options change; stable output MV identity |
| 4 | **`createTransform` ranges** | Each accepts `T[] \| Accessor<T[]>` — keep positional signature unchanged |
| 5 | **Top-level ref args** in `createInView` / `createPan` | Widen to `Accessor<T> \| T` — accept both accessors and static elements |
| 6 | **Nested ref-shaped fields** inside options (e.g. `ViewportOptions.root`) | Static `T` only. Reactivity comes from wrapping the whole options in `Accessor<Options>`. **This is a breaking change** to `ViewportOptions.root`. |
| 7 | **`DragConstraints` per-field accessor** (`() => HTMLElement \| null` arm) | Drop the function arm — static `HTMLElement \| { top, left, right, bottom }` only. Reactivity comes from wrapping `MotionOptions` in an accessor. **Breaking change** to `DragConstraints`. |
| 8 | **`createMotion` signature** | Widen to `MotionOptions \| Accessor<MotionOptions>` — same as `useMotion`. The imperative primitive shouldn't be stricter than the wrapper. |
| 9 | **Versioning** | `0.2.0` — minor bump (pre-1.0 semver allows breaking on minor). Document each breaking migration explicitly. |

**Principle underlying #6:** if `Accessor<Options>` is the canonical reactive
escape hatch, individual fields inside options don't also need to be
accessors. One consistent reactivity layer, not two. Existing call sites that
pass `root: () => rootEl` migrate to `options: () => ({ root: rootEl() })`.

### 4.6 `createSpring` — reactive options, stable output MV, preserve visual position

[`packages/motion/src/primitives/motion-value.ts`](../../packages/motion/src/primitives/motion-value.ts) around lines 208-225:

```diff
 export function createSpring(
   source: MotionValue<number> | Accessor<number>,
-  options?: SpringOptions,
+  options?: SpringOptions | Accessor<SpringOptions>,
 ): MotionValueAccessor<number> {
-  if (isMotionValue(source)) {
-    const mv = springValue(source as MotionValue<number>, options)
-    onCleanup(() => mv.destroy())
-    return makeAccessor(mv)
-  }
-  // Accessor input — bridge through an intermediate MotionValue that mirrors it.
-  const bridge = motionValue((source as Accessor<number>)())
-  onCleanup(() => bridge.destroy())
-  createComputed(() => bridge.set((source as Accessor<number>)()))
-  const mv = springValue(bridge, options)
-  onCleanup(() => mv.destroy())
-  return makeAccessor(mv)
+  const getOpts = typeof options === "function" ? options : () => options
+
+  // ---- Stable bridge MV ----
+  // Mirrors the source. For an MV source it IS the source (do NOT destroy on
+  // cleanup — that would tear down the caller's MV). For an Accessor source
+  // we own an intermediate MV driven by the signal.
+  let bridge: MotionValue<number>
+  if (isMotionValue(source)) {
+    bridge = source as MotionValue<number>
+  } else {
+    bridge = motionValue((source as Accessor<number>)())
+    onCleanup(() => bridge.destroy())
+    createComputed(() => bridge.set((source as Accessor<number>)()))
+  }
+
+  // ---- Stable output MV ----
+  // Identity MUST survive opts changes so existing `.on("change")` listeners
+  // and `useMotion({ animate: { x: spring } })` references keep working.
+  const out = motionValue(bridge.get())
+  onCleanup(() => out.destroy())
+
+  // ---- Per-iteration spring + tempSource (preserve-position pattern) ----
+  // Naive rewrite would recreate the spring directly on `bridge`. Because
+  // springValue's internal position is initialized from its source's CURRENT
+  // value, doing so makes the new spring start at `bridge.get()` — which
+  // VISUALLY SNAPS `out` from its mid-flight value to the input value the
+  // moment the user retunes. The whole point of reactive opts is the
+  // spring REACTING, not teleporting.
+  //
+  // Fix: per iteration, build a tempSource MV initialized at the current
+  // visual position (`out.get()`). The new spring starts there; we then
+  // immediately set tempSource to `bridge.get()` so the spring has work to
+  // do. A subscription on `bridge` keeps tempSource tracking the live target
+  // for the rest of this iteration's lifetime.
+  //
+  // Velocity still resets to 0 — motion-dom's springValue has no public API
+  // for seeding initial velocity. This is an honest documented limitation.
+  createComputed(() => {
+    const opts = getOpts()
+    const startPos = out.get()
+
+    const tempSource = motionValue(startPos)
+    onCleanup(() => tempSource.destroy())
+    const spring = springValue(tempSource, opts)
+    onCleanup(() => spring.destroy())
+
+    // Spring drives out.
+    onCleanup(spring.on("change", (v) => out.set(v)))
+
+    // Kick the spring toward the live target.
+    tempSource.set(bridge.get())
+
+    // Pipe future bridge changes into tempSource so the spring keeps chasing.
+    onCleanup(bridge.on("change", (v) => tempSource.set(v)))
+  })
+
+  return makeAccessor(out)
 }
```

**Critical #1 — output MV identity stability.** `out` is allocated ONCE outside
the `createComputed`. If you accidentally return a new `makeAccessor(...)` per
opts change, consumers' `.on()` subscriptions silently break. Covered by the
identity-preservation test in §5.

**Critical #2 — position continuity on retune.** The tempSource pattern is
load-bearing. A regression that wires the spring directly onto `bridge` will
re-introduce the jump (`out` snaps to `bridge.get()` instantly). Covered by the
position-continuity test in §5.

**Semantic to document (CHANGELOG + JSDoc):** retuning the spring mid-flight
preserves the visual position but resets internal velocity to 0. If users want
to retain velocity, they need to wrap their opts in `createMemo` to avoid
recreates entirely — or stiffen/dampen via a transition's `velocity` field
imperatively. This caveat is honest and documented.

+  // createComputed, so its cleanup (whether via onCleanup for MV inputs
+  // or createComputed for accessor inputs) is iteration-scoped — the
+  // previous subscription tears down before the new mapper takes over.
+  //

+  // for an Accessor input, a naked read would subscribe the OUTER
+  // createComputed to `input`, causing the mapper to rebuild on every
+  // input tick instead of only on ranges/opts changes. Input tracking
+  // belongs to the inner `subscribeInput`, not the outer.

Add `untrack` to the `solid-js` import in this file.

**Critical #1 — outer-construction `untrack` (initial seed BEFORE the
createComputed).** If you forget it, the outer owner subscribes to the range
signals (because the eager `getInputRange()` runs during the calling
component's body), and changes to those signals would re-run the *component*
instead of just the inner `createComputed`.

**Critical #2 — inner `untrack` on the eager input read (inside the
createComputed).** For Accessor inputs, the eager `readInputValue(input)` line
would subscribe the OUTER `createComputed` to `input` — causing the mapper to
be rebuilt on every input tick (negating the whole point of the inner
`subscribeInput`). The inner `untrack` quarantines input tracking to the
inner subscription. Covered by the mapper-rebuild-count test in §5.

#### `createSpring` — position continuity across opts retune (Q3 Option B)

This test is the safeguard against a regression that wires the new spring
directly onto `bridge` instead of through the tempSource pattern. Without the
tempSource, `smooth.get()` snaps to `bridge.get()` the moment opts change;
this test would fail.

```ts
it("preserves visual position when options change mid-flight", async () => {
  const x = createMotionValue(0)
  const [opts, setOpts] = createSignal<SpringOptions>({ stiffness: 100, damping: 20 })
  const smooth = createSpring(x, opts)

  // Drive the spring mid-flight.
  x.set(100)
  await flushFrames()                            // let several frames elapse
  const beforeRetune = smooth.get()
  expect(beforeRetune).toBeGreaterThan(0)
  expect(beforeRetune).toBeLessThan(100)         // confirm we're mid-flight

  // Retune.
  setOpts({ stiffness: 50, damping: 30 })
  await Promise.resolve()                        // let createComputed flush

  const afterRetune = smooth.get()
  // Position continuity within epsilon — NOT a jump to bridge.get() (= 100).
  expect(Math.abs(afterRetune - beforeRetune)).toBeLessThan(1)
})
```

This test catches the bug where the outer `createComputed` tracks `input` and
rebuilds the mapper on every input tick. With the inner `untrack` in place,
mapper builds should happen exactly once at construction + once per ranges/
opts change, NEVER per input change.

```ts

  // shape below assumes a `vi.spyOn(motionModule, "transform")` setup.
  const transformSpy = vi.spyOn(motion, "transform")

## 7. CHANGELOG draft

Append to [`packages/motion/CHANGELOG.md`](../../packages/motion/CHANGELOG.md):

```markdown
## [0.2.0] — YYYY-MM-DD

### Breaking

- **`ViewportOptions.root` is now `Element | null` instead of `() => Element | null`.**
  Reactivity moves up to the whole-options accessor. Migration:

  ```ts
  // before (0.1.x)
  createInView(el, { root: () => rootEl() })

  // after (0.2.0) — createInView direct
  createInView(el, () => ({ root: rootEl() }))

  // after (0.2.0) — useMotion's inViewOptions
  useMotion(() => ({ animate: ..., inViewOptions: { root: rootEl() } }))
  ```

  Affects `createInView`'s options and `MotionOptions.inViewOptions`. Note:
  `inViewOptions` itself is NOT accessor-shaped — reactivity comes from
  wrapping the surrounding `MotionOptions` in an accessor.

- **`DragConstraints` no longer accepts a function arm.** The
  `() => HTMLElement | null` variant is removed. Static `HTMLElement` or
  the rect-object form (`{ top, left, right, bottom }`) only. Reactivity
  comes from wrapping the whole `MotionOptions` in an accessor:

  ```ts
  // before (0.1.x)
  useMotion({ drag: true, dragConstraints: () => containerEl() })

  // after (0.2.0)
  useMotion(() => ({ drag: true, dragConstraints: containerEl() }))
  ```

- **`createScroll` options dropped per-field accessors.** `container` and
  `target` are now static `Element | null`. Reactivity comes from wrapping
  the whole options in an accessor:

  ```ts
  // before (0.1.x)
  createScroll({ container: () => containerEl() })

  // after (0.2.0)
  createScroll(() => ({ container: containerEl() }))
  ```

### Changed

- **Every primitive that takes options now accepts `Accessor<Options> | Options`.**
  Standardized on Solid's `Accessor<T>` type alias across the public surface.
  Affects `useMotion`, `createMotion`, `createScroll`, `createInView`,
  `createPan`. Existing call sites using either the static or function form
  continue to compile — the static-object call sites were always accepted,
  and the previous `() => Options` shape is structurally identical to
  `Accessor<Options>`.

- **Top-level refs in `createInView` and `createPan` now accept a static
  `Element` in addition to an accessor.** Previously these only accepted the
  function form. Existing accessor call sites are unchanged. Note: static-ref
  call sites are captured ONCE; they do NOT re-attach when the variable
  changes — use the accessor form for reactive refs.

### Added

- **`createSpring` and `createTransform` accept reactive options.** When
  options (or, for `createTransform`, the input/output ranges) change, the
  underlying spring or transform engine is recreated; the output
  `MotionValueAccessor` identity is preserved so existing `.on("change")`
  subscriptions and `useMotion({ animate: { x: spring } })` references
  continue to work.

  `createSpring` retunes mid-flight **preserve the visual position** (via an
  internal tempSource pattern) but reset internal velocity to 0 — there is
  no public motion-dom API for seeding initial velocity. If you need to
  retain velocity across a retune, wrap your options in `createMemo` so
  recreates only happen on coarse-grained changes.

- **Layout animations.** [Layout animations CHANGELOG section — fill in
  based on what ships in 0.2.0.]
```

## 8. Migration guide (for the release notes / blog post)

> If you're upgrading from 0.1.x:
>
> 1. **`createInView` direct call — `root` field** — change
>    `createInView(el, { root: () => rootEl })` to either:
>    - `createInView(el, { root: rootEl })` — locks `root` at construction.
>    - `createInView(el, () => ({ root: rootEl() }))` — keeps reactivity.
>
> 2. **`useMotion`'s `inViewOptions.root`** — `inViewOptions` is NOT
>    accessor-shaped. To make `root` reactive, wrap the surrounding
>    `MotionOptions` in an accessor:
>    ```ts
>    // before (0.1.x)
>    useMotion({ animate: ..., inViewOptions: { root: () => rootEl() } })
>
>    // after (0.2.0)
>    useMotion(() => ({ animate: ..., inViewOptions: { root: rootEl() } }))
>    ```
>
> 3. **`useMotion`'s `dragConstraints` function form** — same pattern.
>    `dragConstraints` is no longer `() => HTMLElement | null`; reactivity
>    comes from wrapping `MotionOptions`:
>    ```ts
>    // before (0.1.x)
>    useMotion({ drag: true, dragConstraints: () => containerEl() })
>
>    // after (0.2.0)
>    useMotion(() => ({ drag: true, dragConstraints: containerEl() }))
>    ```
>
> 4. **`createScroll`** — if you pass `container: () => el` or
>    `target: () => el`, change to the whole-options accessor form:
>    `createScroll(() => ({ container: el() }))`. The static form
>    `createScroll({ container: someEl })` works too — but doesn't track
>    signal changes.
>
> 5. **Reactive `createSpring` retunes feel different.** If you were already
>    passing reactive options (you weren't — this wasn't supported in 0.1.x),
>    note that retuning mid-flight now preserves the visual position but
>    resets internal velocity. New behavior, not a migration concern.
>
> 6. **Everything else** — no source changes required. `useMotion`,
>    `createMotion`, `createPan`, `createSpring`, `createTransform` all keep
>    their existing call shapes; we widened them rather than tightened.

## 9. Risk list (read this before merging)

1. **Output MV identity must remain stable for `createSpring` / `createTransform`.**
   The single biggest hazard. If `out` is rebuilt per opts change instead of
   bridged-into, every consumer with a stashed `.on("change")` subscription
   silently breaks. The dedicated identity test in §5.2 covers this — make
   sure it fails against a buggy implementation before declaring done.

2. **`createSpring` position continuity on retune (Q3/Option B).** The
   tempSource pattern is load-bearing. A naïve rewrite that wires the new
   spring directly onto `bridge` re-introduces the visual jump
   (`smooth.get()` snaps to `bridge.get()` on every retune). Covered by the
   position-continuity test in §5.2 — that test MUST fail against the naïve
   version before passing against the tempSource version.

3. **`untrack` in `createTransform` — TWO placements needed.**
   - **Outer-construction:** the initial-seed `motionTransform(...)` call
     outside the `createComputed` must use `untrack` on each getter to
     avoid leaking subscriptions to the calling owner.
   - **Inner-iteration:** the eager `readInputValue(input)` inside the
     `createComputed` must also be wrapped in `untrack`, or the outer
     computed subscribes to `input` and rebuilds the mapper on every input
     tick (defeating the point of the inner `subscribeInput`). Covered by
     the mapper-rebuild-count test in §5.2.

4. **Spring velocity loss on retune.** Documented behavior — position is
   preserved but internal velocity resets to 0. Users won't typically
   notice unless they retune at high frequency. The CHANGELOG note and
   `createSpring` JSDoc both call this out.

5. **Options-accessor churn.** A high-frequency signal feeding into an
   accessor that returns a fresh options object every read causes constant
   recreate. For `createSpring` this means the spring never settles. We
   don't add internal memoization (every primitive trusts the caller's
   reactivity discipline) — JSDoc the caveat.

6. **`ViewportOptions.root` migration confusion.** The TS error from
   `root: () => rootEl` is clear, but the migration path needs to be
   spelled out (done in §7 and §8) so users don't write `root: rootEl`
   (where `rootEl` is still a signal) and lose reactivity without
   realizing. Symmetric concern applies to `DragConstraints` (Q1).

7. **Ref-widening semantics for static refs.** `createInView(staticEl, opts)`
   and `createPan(staticEl, opts)` capture the ref once; reassignment of
   the variable won't be picked up. The footgun: `createInView(el())`
   where `el` is a signal silently passes the CURRENT value, not the
   accessor — TypeScript allows it because both forms are now accepted.
   JSDoc the distinction loudly. Static-ref tests in §5.2 (createInView +
   createPan) lock the supported shape; they also serve as the canonical
   example for users.

8. **`createMotion` widening fallout.** `createMotion` is re-exported and
   may have third-party consumers. The widening is purely additive
   (function form still accepted), so no breakage — but worth a CHANGELOG
   mention so users know they CAN now pass a static options object.

9. **`DragConstraints` widening fallout.** The resolver in
   [`createDrag.ts`](../../packages/motion/src/primitives/createDrag.ts)
   around line 413 currently handles the function arm. Removing it
   simplifies the resolver but requires migration of any internal test
   that passes the function form. Grep `dragConstraints: () =>` across
   `tests/gestures/*` during execution.

10. **SSR.** All affected primitives are wrapped in `createEffect` /
    `createComputed`, which are no-ops on the server. SSR semantics
    unchanged. Low risk; still worth re-running `bun --filter solidjs-motion test:ssr`
    as part of verification.
